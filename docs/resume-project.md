# 简历项目与面试准备

## 当前 React 前后端分离版本

主界面用 **React + TypeScript + Vite**，通过 REST 调用 **FastAPI + LangGraph**。本机使用模拟手册、固定用户和模拟工单，规模保持在中等难度。演示先跑「IT 提问 → 核对引用 → 编辑草稿 → 确认建单」，再选一条查询对照两种切片。如果只讲三分钟，保留问答、确认与一个失败例子。Telegram 放在扩展追问时介绍。[架构和源码](react-design.md) · [验收与数据](knowledge-lab.md)

完成独立复现并能解释相应模块后，可按真实负责范围使用：

> 构建前后端分离的 IT 服务台演示，使用 React、TypeScript、FastAPI 和 LangGraph。实现有原文引用的手册问答和工单草稿流程，用请求编号恢复问答结果，用 SQLite 事务防止重复创建工单。在同一语料和 Embedding 模型下比较切片策略，逐题核对召回排名与证据覆盖。

可选条目：

- 将原型页面迁移为React组件和TypeScript API层，统一超时、网络及业务错误；区分HTTP成功与Agent业务状态，使用受限CORS支持本机跨域开发。
- 用相同手册、查询和 Embedding 模型比较自然边界与固定窗口，展示两组 Top-K 证据、余弦相似度和切片开销，并记录持平或退化的例子。
- 将前端编辑/确认状态与后端工单事务解耦：保存草稿不等于建单，确认只传已存草稿编号，重复确认返回同一工单；用前端逻辑测试、浏览器关键流程和后端事务测试覆盖。

这些条目描述项目实现，**不自动等于“本人独立手写”**。代码、用例和文档由AI辅助编写/修改；候选人应逐项填写本人独立设计或改写、AI辅助协作、已有基座能力，并能现场修改和验证。React/TypeScript/Vite、LangGraph、Chroma、SQLite和模型已有能力不能计为自研框架。没有新增企业用户数据、模型质量复测或性能对照，不能把迁移写成“准确率/效率提升若干百分比”。

下文保留Python/Streamlit原型与第三、四周的历史表述和原始指标，不能把历史自动化测试数量或模型成绩标为React现版重跑结果。

## v1 与历史评测材料

项目名称：**ITDesk Copilot Lite｜基于证据的IT问答与模拟工单助手**。

项目定位：Python中等规模本地练习，覆盖RAG、有限Agent工具调用、会话持久化、确认与事务幂等、离线评测。使用原创模拟数据，没有企业上线或真实业务收益。代码由AI辅助实现，面试表述应以本人能解释、修改和独立复现的部分为准。

## 可以使用的简历表述

> 基于Python、FastAPI、Streamlit与LangGraph构建本地IT服务台助手，实现知识问答、模拟服务状态/工单查询和需用户确认的工单创建；设计最多3次串行只读工具尝试、结构化输出与本轮引用校验，并通过SQLite事务及draft_id唯一约束避免重复工单。

可按真实负责范围选用以下条目，不必全写：

- 对原创VPN、邮箱、办公设备手册建立Chroma索引，结合向量召回与完整错误码精确匹配，保留原文、版本和片段ID；通过索引指纹拒绝模型或资料变化后的旧索引。
- 将分诊、工具决策和最终结构化生成分开，使用Pydantic、工具白名单和次数上限约束模型；以业务SQLite保存回复/草稿，以AsyncSqliteSaver记录图状态，支持已保存会话恢复和完成请求重放。
- 将工单写入放在固定确认接口，确认只能读取已保存草稿；一个事务完成工单、草稿状态与审计，验证未确认不创建、重复确认不重复和写入故障回滚。
- 建立开发/冻结验收用例、检索消融实验与模型/工具/数据库故障检查，按实际执行模式分别报告分类、召回、答案、时延和用量；逐条答案评分明确为AI辅助来源复核。
- 根据已存失败修订执行边界：合法搜索保留有限用户源完整标识，轨迹区分模型`requested_args`与实际`args`；草稿采用类别固定标题和归因明确的用户原话，数据库维修动作使用确定性范围规则。

可选的量化表述，仅在本人已复现并能解释实验时使用：

> 建立20条开发题与60条冻结验收题；在50条真实模型验收请求上测得类别Macro-F1为0.953（40条业务题为0.931），通过10项独立的确定性故障检查。对28条有来源金标的问题开展同查询检索对比，两策略Recall@5均为1.000，本次未发现错误码组合策略的召回提升。

这些是第三周旧实现的历史结果，运行于2026-11-17，使用`deepseek-v4-flash`与`Qwen/Qwen3-Embedding-8B`，仅覆盖本地虚构资料；不能当成第四周当前代码重跑成绩。50条真实模型题与10条故障注入不能合并成“60条模型题全部通过”；80条是开发加验收总数，不是80条独立真人标注请求。另有68/68个引用ID通过来源集合校验，不能称为100%答案正确率。AI辅助任务正确数49/50、实质回答/草稿证据支持37/38（97.37%），其余12条拒答/澄清未计支持率分母。复核者参与金标编写，并非独立人工；人评目标未验证。费用因单价未配置而未知。

如果要使用量化指标，只引用[第三周历史报告](week3-report.md)或[第四周定向回归报告](week4-report.md)已完成且本人复核过的结果，写明实现版本、样本分母、模型、是否盲测、评分方式和日期。不把类别指标写成整体准确率，不把引用ID写成语义支持率，也不把开发样本、故障替身或框架已有能力算成本人业务成绩。

## 第四周可以讲清的修复

第四周使用独立12题做非盲定向回归：6条旧问题重放、2条类似改写、4条正常/边界对照；其中11条使用真实模型，W403由维修规则直接返回且0模型调用，另有1个真实历史轮次。AI辅助复核任务正确11/12，实质回答/草稿来源支持9/9；W405最终生成超时，保留在任务分母中。135项自动化测试通过。这些结果验证已知问题的修复覆盖，不是独立真人评分，不能直接与第三周50题准确率相减，也不能称12条独立模型验收；具体证据见[报告](week4-report.md)和[交付记录](week4-delivery.md)。

可以按本人已掌握范围表述：

> 针对已存trace中的查询丢码和草稿事实混淆，在工具执行前保留用户源标识，并将持久化草稿改为固定标题、归因明确的用户原话；以定向回归和数据库故障检查验证。将禁用短语匹配作为待复核风险信号，保留旧评测成绩及金标更正记录。

代价和边界也应讲清：原话描述更长、少了语言归纳，用户陈述仍未核实，模型仍可能错判是否提议草稿或类别；标识规则只覆盖既定格式与有限追问来源；数据库维修规则可能漏判/误判；有限凭证遮蔽不等于完整脱敏。`risk_signals`也不能证明安全，通过机械检查之后仍需逐条AI来源复核，真人指标保留未验证。

不应写“服务企业员工”“效率提升某百分比”“生产零事故”“自研Agent框架”“完成真实权限审批”。当前没有相应用户、对照或上线证据。独立负责的范围如果仅为设计、部分模块或复核，应如实缩小表述，不能因为AI生成了代码就声称全部手写。

## 两分钟讲述顺序

1. **具体问题**：假想员工需要查手册、状态和工单；升级人工时要重复描述。数据是模拟的，需求频率没有企业调研证据。
2. **完整链路**：问题进入API，模型分诊/澄清，有限选择只读工具，基于本轮证据生成JSON并校验；草稿保存后由用户按钮确认，再通过事务创建工单。
3. **两个关键取舍**：为什么保留普通代码的确认事务；为什么先用向量加错误码，而不增加搜索集群、重排或多个Agent。给出实际代价和对照证据。
4. **验证与限制**：展示一条真实trace、一个失败案例和冻结评测报告。区分引用存在与语义支持，说明AI辅助评分和固定模拟身份。

一个可讲的真实失败是第三周A033：用户提供蓝屏报修码`DEV-201`，模型却在草稿中写成“设备编号 DEV-201”。合法JSON和引用没挡住语义混淆，[历史逐例复核](../evaluation/reviews/acceptance-workflow-review.json)判为不支持且任务不正确。第四周不再将自由改写的标题/描述保存成用户事实，而以固定类别标题和明确未核实的用户原话替代，并用W404原题、W408真实资产编号/报修码及否定经历改写检查。原始A033成绩保留；当前结果必须按本周报告说明，不能倒改旧题或靠机械规则变化声称模型提升。

## 面试前应能现场完成

| 追问 | 需要打开的实际证据 | 应说清的边界 |
|---|---|---|
| 为什么不是一个普通函数？ | `AgentService`节点/条件边，一条多来源请求trace | 固定流程可以用函数；本项目只研究有限决策，没有证明Agent在所有任务上更好。 |
| 怎么保证最多三次？ | `MAX_TOOL_ATTEMPTS`、`_tools`及额度测试 | 错误参数也扣额度，多工具批次不执行；生成与分诊调用不计成工具执行。 |
| 为什么不只做向量检索？ | 纯向量/错误码结合的同集实验与收益、退化案例 | 精确码规则可能挤掉其他文档，是否有收益看实测，不背“混合检索更好”。 |
| query里为什么补码？ | `grounded_search_args`、`requested_args/args`、D008与W401/W407轨迹 | 当前用户码优先，无码追问仅看最近用户消息，非法参数仍拒绝；保码不证明用户给的码正确。 |
| 怎样防止工单补写事实？ | `sourced_ticket`、D015/A033历史及本周草稿 | 固定标题和原话归因消除后端自由改写，不验证用户陈述，提议/类别仍需核对。 |
| 引用有效就可靠吗？ | `_final`引用集合检查、原文、AI辅助逐条复核表 | ID存在只证明来源可追溯，不能保证整段答案被支持。 |
| 为什么没有Reviewer？ | `live_contract`返回的`risk_signals`、逐条来源复核及`requires_database_change` | 有限规则与离线复核适合当前规模，不将机械通过、0模型规则结果或AI评分当完整安全保证。 |
| 模型说“确认”能不能提交？ | `TOOL_SCHEMAS`、确认API、`EmptyRequest` | 模型没有写工具；只有固定接口读取已存草稿后提交。 |
| 双击、断网和数据库故障怎么办？ | `confirm_draft`事务、唯一draft_id、并发与回滚测试 | 事务防半提交，重试返回同单；不是对所有生产异常的完整保证。 |
| Checkpoint和业务库为何分开？ | `_persist`、`finish_turn`、提交后Checkpoint故障测试 | 业务表是工单事实来源，不能从Checkpoint推断“已创建”；没有跨库事务。 |
| 谁做的，哪些是框架能力？ | 实际能解释的代码、测试和本地改动 | 如实承认AI辅助，区分个人设计/验证与框架、模型、模拟数据。 |

## 个人负责范围如何填写

现有文件只能证明项目产物与检查，不能证明候选人连续投入了四周或手写全部代码。投递前按自己的实际情况填写，而不是直接把仓库功能清单全部改成“本人独立完成”：

| 范围 | 应填写的实际内容 |
|---|---|
| 本人独立完成 | 不依赖提示能复现的模块、自己做出的设计选择，以及自己改写并验证的内容；尚未独立完成的留空。 |
| AI辅助或协作完成 | AI生成/修改过的代码、用例、文档与逐例评审；说明本人如何阅读、验证和修正。 |
| 已有基座能力 | 模型的理解/生成/tool calling，LangGraph图执行与Checkpointer，Chroma向量检索，SQLite事务与唯一约束等。项目负责组合、接口约束和验证。 |
