# 五分钟演示脚本

> 本文是历史演示脚本。请按[现版 README](../README.md)启动 React 工作台。重现旧界面须使用[原型归档](streamlit-retirement.md)。

目标是展示可验证的闭环和边界：有来源的回答、无证据拒答、状态查询、工单确认，以及受控失败。示例资料、服务状态与工单均为模拟数据。真实模型可能有波动；报告中的失败也应展示，不只挑选成功样本。

## 演示前准备

在仓库根目录按 README 配置 `.env`、安装锁定依赖并建立索引。两个终端分别运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-api.ps1
powershell -ExecutionPolicy Bypass -File .\scripts\start-ui.ps1
```

打开 <http://127.0.0.1:8501>，确认24篇手册索引就绪。不要在演示中打开`.env`。提前查看[第三周实测报告](week3-report.md)，准备一个实际失败案例及对应原始结果；它与下面的确定性故障演示用途不同。

## 0:00–0:35：问题与架构

讲述：“这是本地模拟IT服务台。模型理解问题、选择三个只读工具并整理答案；普通代码控制工具次数、来源、用户确认与事务。它没有真实企业登录或设备操作权限。”

打开[最终设计研究](final-design.md)的架构图，指出LLM、检索、业务SQLite、Checkpoint与固定确认接口。不要逐一讲解所有依赖。

## 0:35–1:30：知识问答和证据

新建会话，输入：

> VPN-403 设备未授权，应该先怎么排查？

展开回答依据，展示来源、版本与原始片段；再展开工具轨迹，指出`search_knowledge`的实际参数与返回。解释完整错误码匹配为何需要与向量召回结合，但收益取决于实测对比；引用存在不等于每句话语义都正确。

追问：

> 那这个服务在模拟系统中正常吗？

展示本轮重新调用`get_service_status`。指出这是带日期的固定模拟快照，不能当真实企业监控；历史用于理解“这个服务”的指代。

## 1:30–2:05：信息不足与拒答

另开会话，输入“帮我处理一下”，展示缺失信息提示，以及没有执行工具的分支。随后输入：

> 公司是否提供员工住房补贴？

展示无证据拒答。说明系统没有住房制度资料，不应该为了回答而编造政策。若模型这次行为与预期不同，展开trace说明实际走法，引用报告中的已知失败，不把“流程结束”称为“答案正确”。

## 2:05–3:35：草稿与显式确认

回到VPN会话，输入：

> 按手册排查后仍然失败，请整理一张工单草稿，交给人工核对设备登记。

检查标题、描述、分类。明确区分用户报告与已查证事实。此时只存在pending草稿，展开“我的模拟工单”说明还没有该草稿对应的新工单。可以在聊天里输入“确认”，说明这仍只是聊天，不能代替页面按钮。

点击“确认创建工单”，展示返回编号与工单列表。解释确认接口只接收草稿ID和空对象、字段从数据库读取，事务同时创建工单、更新草稿和写审计。重复确认不会新增第二张工单；可使用下方API片段演示，不依赖重复点击已经隐藏的按钮。

再提出一个打印问题草稿并点击“取消草稿”，说明取消后不能提交。若现场时间不足，展示报告中已执行的取消与重试证据；不要声称现场已执行未展示的步骤。

## 3:35–4:20：失败与恢复

打开已有会话URL后刷新，展示服务端历史和当前草稿状态恢复。说明当前只承诺恢复已保存会话与草稿，进程中断的未完成轮次需使用新请求ID重新提问，未实现任意节点自动续跑。

在项目终端运行确定性故障检查：

```powershell
.\.venv\Scripts\python.exe -m evaluation.run --split acceptance --faults-only
# 同一目录已存在且代码/配置一致时，重复演示使用 --resume，或指定新的 --output。
# --resume 只补未完成项；要再次执行10条故障，应选择新的输出目录。
```

选取模型超时或SQLite审计失败的输出，解释其注入位置、观察结果与断言：请求明确失败，或整个事务回滚，不显示假成功。这一部分使用模型替身与本机临时数据，不是对真实服务商故障率的统计。

## 4:20–5:00：实测结果与个人工作

打开第三周报告，只讲该文件已记录的数字：冻结业务/异常用例范围、类别/意图、Recall@5及检索对比、引用与AI辅助证据评分、P50/P95、Token、未知费用和失败案例。说明开发与冻结验收分开，故障注入没有混入真实模型成功率。

结束时讲：“我能解释并复现状态图、工具边界、检索组合、引用校验和确认事务；模型与框架能力来自现有基座，代码由AI辅助实现。这个练习没有生产用户或企业效率收益数据。”

## 可选API演示：同一草稿重复确认

在页面已有pending草稿后，用API文档或读取会话详情获取真实`draft_id`，替换下例。不要复制演示占位ID发送请求。

```powershell
$draftId = '替换为本机真实草稿编号'
$first = Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/drafts/$draftId/confirm" -ContentType 'application/json' -Body '{}'
$second = Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8000/api/drafts/$draftId/confirm" -ContentType 'application/json' -Body '{}'
$first.ticket.ticket_id
$second.ticket.ticket_id
```

两个编号应相同；如果响应失败，应检查错误而非声称确认成功。确认body增加`title`或`user_id`等字段会被拒绝，它不能修改已展示草稿。该操作只创建本地模拟工单，不发送通知或接入企业IT系统。
