# 第三周评测集与冻结规则

这里保存80条原创模拟案例：`dev.json` 20条开发题、`acceptance.json` 60条验收题。题目与金标依据当前24篇模拟手册、固定服务快照、种子工单及后端边界整理，**由AI辅助逐条核对源码，并非独立真人标注，也不代表生产请求分布**。题目编写时没有读取本轮模型执行结果或据此调整金标。

## 划分与计数

| 文件/分组 | 数量 | 内容与执行口径 |
|---|---:|---|
| 开发集 | 20 | 10知识、3服务状态、1本人工单、2草稿、2澄清、2无证据；均为真实API可执行题。 |
| 验收业务题 A001–A040 | 40 | 24知识题覆盖全部24篇手册，3服务状态、3本人/不可见/不存在工单、4草稿、3澄清、3多轮。 |
| 验收异常/安全题 A041–A050 | 10 | 知识库外、未知系统、完整错误码、绕过确认、伪造写工具、伪造身份、索取密钥、凭证与证书边界、模拟快照冒充实时状态；调用真实API。 |
| 验收故障注入 A51–A60 | 10 | 模型超时/非法JSON、工具超时、索引不可用、SQLite写失败、未确认、取消后确认、重复确认、外人工单、文档注入；用确定性替身和临时真实SQLite执行。 |

因此验收集是 **40业务 + 20异常/安全**；其中50条可作为真实模型评测案例，10条验证确定性工程不变量。不能将故障替身成绩并入真实模型分类、召回或答案质量分母。开发题和验收题的问题文本互不重复，也不与第一周开发题完全重复；同一业务主题、相同资料和错误码在小型知识库中会重复，这不是域外泛化验证。

三条多轮题的 `history` 是需要先实际执行的用户问题，不是凭空注入的已验证系统事实。最终问题为该案例的主要评分对象；报告必须单独注明历史轮次的额外调用、时延和Token，不能把一条多轮案例当作一条无上下文请求。

## 字段契约

根对象为 `{schema_version,split,description,cases}`。每个case包含：

| 字段 | 含义 |
|---|---|
| `id`、`split` | D001–D020；验收实际ID为A001–A050及A51–A60，开发/验收划分。 |
| `kind`、`scenario` | 业务/异常分组及具体场景；故障题不参与模型质量分母。 |
| `execution_mode` | `live`调用真实Provider；`fault`走故障注入。 |
| `question`、`history` | 当前问题与先行用户问题；正文均为模拟数据。 |
| `expected.category`、`expected.intent` | 当前问题的分类金标。优先级是建议值，未设置可验证的紧急程度金标，不用于准确率。 |
| `expected.status` | 允许状态数组；明确业务场景只有一个。少数安全题允许安全澄清/拒答，不能把这解释为唯一正确回答。故障题的状态用于解释，不替代命名不变量检查；SQLite故障观察值为`storage_error`。 |
| `expected.doc_ids` | 可回答知识题所需来源文档；对应`knowledge/<category>/<id>.md`。其他场景为空，不能算进知识召回分母。 |
| `expected.required_tool` | 该题应实际使用的只读工具，或null。不要求固定规划次数或固定措辞。 |
| `expected.reference_facts` | 2–3条核心知识事实、状态事实或安全不变量，供逐题证据复核；不是必须逐字匹配的完整答案模板。 |
| `expected.must_not_contain` | 少量肯定式危险行为/泄漏断言的提示信号。字符串命中只能作初筛，不能代替语义复核，尤其要区分否定、引用与真正建议。 |
| `expected.source_files` | 金标依据的手册文件或应用源码符号；源码不是提供给模型的知识证据。 |
| `expected.no_unconfirmed_ticket` | 所有案例都必须满足未调用确认接口就无新增工单。 |
| `fault` | null或10种约定故障标识；故障runner报告独立`passed/checks/observed`。 |

故障标识固定为：`model_timeout`、`model_bad_json`、`tool_timeout`、`index_unavailable`、`sqlite_write_failure`、`unconfirmed_write`、`cancelled_confirm`、`duplicate_confirmation`、`foreign_ticket`、`prompt_injection_document`。

## 冻结与报告纪律

1. 在第一次验收执行前，对两个JSON文件计算SHA-256，记录时间、源码版本/摘要、模型名称、索引指纹及参数。预期答案中的原始资料应能被独立打开复核。
2. 开发题可供调试；验收题运行后保持题目与金标不变。不因某题模型表现不好就重写题目、放宽状态或去掉题目。发现金标事实错误，应公开更正原因、记录新版本，再将已有运行标作旧版本，不能悄悄覆盖。
3. 验收若发现缺陷，报告首轮结果和修复原因；再跑时另存结果并明确同一验收集已暴露，不能声称仍是从未见过的盲测。
4. 分类、工具、召回、引用ID、状态、写入边界可自动核对。`reference_facts`用于逐条对照回答与实际检索原文，质量报告需区分支持、部分支持、不支持和无法判断；引用ID存在不能证明语义支持。
5. AI辅助复核必须标为AI辅助，不能冒称真人人工支持率。若真人参与，应另记评审者、日期、逐题判定及分歧处理。没有真人评分时，原计划的“人工证据支持率≥85%”属于尚未验证指标。
6. 报告无证据题误答、应该澄清却直接回答、漏召回、错误工具、模型/工具失败、未确认写入和重复确认的具体案例。时延与费用保留真实失败；失败用量可能缺失时费用未知，不记为零。

检索对比应在同一冻结题、同一向量索引、同一Embedding和Top5/阈值下，仅改变“是否使用完整错误码优先及同文档邻片段”。这项对比衡量现有两种检索策略，不能声称完整RRF、全文检索或重排实验；无错误码题理论上应一致，错误码题可能提升也可能挤出相关片段，须保留退化案例。
